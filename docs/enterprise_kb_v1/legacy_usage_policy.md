# 旧工作区使用策略

> 版本: v1-draft | 状态: policy | 最后更新: 2026-07-04

---

## 一、旧工作区定义

| 属性 | 值 |
|------|-----|
| 路径 | `E:\Woker` |
| 状态 | **只读** — 不移动、不修改、不删除任何文件 |
| 用途 | 历史参考和研究素材 |
| 访问 | 可读取特定文件用于研究，但不可整体导入 |

---

## 二、禁止事项

以下行为**严禁**：

1. ❌ 将旧工作区的语料文件直接复制到新知识库
2. ❌ 将旧工作区的评测数据直接作为新评测用例
3. ❌ 将旧工作区的 report / forensic / audit 文档直接作为知识库内容
4. ❌ 将旧工作区的 Chroma 数据库/embedding 文件迁移到新工作区
5. ❌ 在新工作区代码中硬编码旧工作区的路径
6. ❌ 用旧评测指标作为新知识库的验收标准

---

## 三、允许的提炼方式

旧工作区内容只能通过以下方式**间接利用**：

### 3.1 Runbook 提炼

从旧故障记录中提取通用排查流程，**不引用具体旧文件路径**：

```
✅ 正确: "当 Chroma collection 返回空结果时，检查 persist_dir 路径是否存在、embedding 维度是否匹配"
❌ 错误: "参考旧工作区中的某个历史评测 JSON 文件得出的结论"
```

### 3.2 Failure Pattern 提炼

提取已知失败模式，不带旧实验编号：

```
✅ 正确: "中文自然语言查询 + 纯英文技术文档 → relevance_score 偏低，需多语言 embedding"
❌ 错误: "旧的 chunking ablation 实验证明 69% bad case 来自 chunk_size 问题"
```

### 3.3 Eval Case 提炼

从旧评测中筛选代表性 query，按新 eval case 格式重写：

```
✅ 正确: 按 core_eval_30 的 JSONL 格式写入新 case，包含 case_id/query/expected_domain/required_answer_points
❌ 错误: 直接复制旧工作区中的历史评测用例 JSONL 文件
```

### 3.4 Policy Lesson 提炼

将旧评测发现转化为工程规范：

```
✅ 正确: "知识库中 policy 类文档的 authority_level 必须高于 implemented"
❌ 错误: "使用旧实验编号证明当前知识库质量，直接复制历史补丁实验结论"
```

## 四、溯源标记

从旧工作区提炼的内容，在 source_registry 中标记为：

```yaml
doc_status: legacy_derived
notes: >
  从旧工作区 (E:\Woker) 经验提炼。
  已改写为通用表述，不包含旧路径/旧文件名/旧实验编号。
  待审核确认后可改为 implemented。
```

---

## 五、豁免场景

以下场景可以使用旧工作区内容：

1. **代码 diff 对比** — 比较新旧 `src/` 代码差异，确认迁移完整性
2. **配置参考** — 参考旧 `.env.example` 确认需要迁移的配置项
3. **文档结构参考** — 参考旧文档的组织形式（非内容）

上述豁免仅限于"参考"，不可直接复制内容。
